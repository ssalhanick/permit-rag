## Today's work: root-causing the query_deconstructor 100% error rate

Machine B's `scripts/run_agent_eval.py` output showed `query_deconstructor`
at `det=0.00 err=1.00`. Investigated by reading code only (this machine's
local DB is empty, per the two-machine split — nothing here could be run
against real data).

Finding: `deconstruct()` in `rag/agents/deconstructor.py` is deliberately
designed to never raise — any `run_agent()` failure is caught and it
degrades to the single-question form, invisible to the Manager and the user
(`_deconstruct` in `manager.py` has its own second layer of the same
try/except). But `run_agent()` itself (`rag/agent_runtime.py:360-367`)
records a `status="error"` row to `agent_steps` for `agent_name=
"query_deconstructor"` *before* the exception is re-raised and caught by
the caller. So a 100% error rate here means every recorded model-call
attempt for this agent in the window failed at the API level — the
graceful-degrade design means this is completely invisible in the live
product, but the telemetry is still catching something real underneath.

Also relevant: the cheap deterministic path (`_looks_compound()` returns
false) never calls `run_agent()` at all, so it never writes an `agent_steps`
row — meaning `query_deconstructor`'s `deterministic_rate` in the scorecard
structurally reads near-zero regardless of how often the free path actually
fires, because only the LLM-invoking branch is ever visible to
`agent_scorecard()`. Separately, `query_deconstructor` has no entry in
`evaluation/agent_eval.py`'s `CONTRACTS` dict — it only inherits
`GLOBAL_CHECKS` (`error_rate ≤ 0.05`), which is what's tripping here.

**Not yet distinguished, needs Machine B:** whether the underlying model-call
failures are an environment/credential issue (an invalid `ANTHROPIC_API_KEY`
was found and is recorded as a known issue on a different session/branch,
2026-08-01 — unconfirmed whether it's the same cause here or already fixed)
or a real bug specific to this call (e.g. the `Deconstruction` structured
output schema, `Tier.CHEAP` + `effort="low"` combination). Recommend on
Machine B: pull a few of the actual `agent_steps.error` messages for
`query_deconstructor` in the window directly (`SELECT error FROM
agent_steps WHERE agent_name='query_deconstructor' AND status <> 'ok'`) —
that will settle it in one query rather than more code reading.

## Same-day follow-up: query_deconstructor root-caused and fixed

Scott ran the recommended one-query check on Machine B via a new read-only
diagnostic script, `scripts/check_query_deconstructor_errors.py`
(`--local`/`--database-url`, follows the `_db_target.py` pattern — the
original inline `python -c` one-liner didn't survive PowerShell, which
reserves `<` for redirection).

Result: all 10 most recent recorded steps, spanning 2026-07-27 through
2026-08-06, failed with the identical error:

```
BadRequestError: Error code: 400 - {'type': 'error', 'error': {'type':
'invalid_request_error', 'message': 'This model does not support the
effort parameter.'}}
```

This settles it decisively — not a credential/environment flake, not a
data-sparsity artifact. A real, 100%-reproducible bug: whatever model
`Tier.CHEAP` resolves to has never actually supported the
`output_config={"effort": ...}` knob that `rag/agent_runtime.py`'s own
module docstring assumed it did ("the model ladder — cheap = haiku... with
`output_config={"effort": "low"}` on cheap-tier subagent calls"). Every real
call from `deconstructor.py` (`effort="low"`) has 400'd since at least
2026-07-27 — meaning Query Deconstructor's actual sub-question splitting
has never once executed successfully via the model path; `deconstruct()`'s
deliberate graceful-degrade design made this completely invisible to users,
but the telemetry caught it. `permit_strategy.py` uses the same
`effort="low"` call shape and would hit the identical bug on its LLM path
(its route currently calls `plan_permits(use_llm=False)`, so it's likely
dormant there rather than actively broken in the same visible way).

**Fixed** in `rag/agent_runtime.py`, mirroring the existing precedent
exactly: `_dispatch` already learns per-model when `temperature` is
rejected (`_TEMPERATURE_UNSUPPORTED`, added for Sonnet 5/Opus 4.8) and
retries without it. Added the identical pattern for `effort`/
`output_config` — a new `_EFFORT_UNSUPPORTED` set, `_is_effort_unsupported()`
detecting the 400 message, and `_call()` now takes `include_output_config`
alongside the existing `include_temperature` so either knob can be dropped
independently on retry. Two new tests
(`test_effort_unsupported_retries_without_it`,
`test_effort_unsupported_model_skips_it_from_the_start`) mirror the
existing temperature-retry test pair exactly. 841 tests passing (839 + 2
new), ruff clean — machine A, mocked only. **Not yet committed** (pending
go-ahead) and **not yet re-verified against real Machine B traffic** — same
sequential-gating discipline as any `agent_runtime.py` change: re-run
`check_query_deconstructor_errors.py --local` after this lands to confirm
live calls actually succeed now, don't just trust the mocked tests.

## Hand-check: a second, more serious bug found and fixed

Wrote `scripts/hand_check_deconstructor_fanout.py` to finally do the
compound-query hand-check STATE.md's Phase 5 tail has called for since
before this session started — comparing fan-out retrieval against
single-question retrieval on 3 real compound queries (Plano
setback+height+electrical, Dallas bathroom-remodel+ADA, Fort Worth
stormwater+fire-sprinkler).

Result was not "fan-out helps" or "fan-out doesn't help" — it was fan-out
silently broken in a new way:
- Plano and Fort Worth queries: **0 fan-out chunks**, vs. 5 real chunks from
  single-question retrieval.
- Dallas query: fan-out returned 5 chunks, but **all from the one
  sub-question with no municipality filter** (the ADA one) — the actual
  Dallas-permit sub-question contributed nothing. Fan-out's result was 100%
  ADA content with the user's real question dropped.

Root cause: `get_jurisdiction_chain()` (`db/client.py:104`) does an
exact-match SQL lookup against the corpus's canonical lowercase/aliased
jurisdiction ids (`rag/jurisdiction_ids.py` exists specifically for this —
e.g. the documented `"fort-worth"` → `"fortworth"` collision). `_resolve_municipality`
already canonicalizes before use; `_fanout_retrieval` never did — it passed
the Deconstructor's raw LLM output (`"Plano"`, `"Fort Worth"`, `"Dallas"`)
straight through. Every real sub-question naming a city silently matched
zero corpus documents.

**Production impact if merged unfixed:** the Plano/Fort Worth shape (empty
merge) gracefully falls back to single-question via `_fanout_retrieval(state)
or _single_retrieval(state)` — no worse than before today's effort-parameter
fix. The Dallas shape (non-empty but one-sided) does **not** fall back —
production would have silently served an incomplete, wrong-focus answer for
any compound query naming a city alongside an unfiltered sub-question,
which is likely a common real query shape.

Fixed in `rag/agents/manager.py`: `muni = canonicalize(getattr(sub,
"municipality", None)) or state.effective_municipality`. Added
`test_fanout_canonicalizes_sub_question_municipality` to
`tests/test_deconstructor_wire.py` — the existing fan-out test suite had
zero coverage of a sub-question carrying its own municipality distinct from
`state.effective_municipality` (every existing test either passed no
municipality or relied on `state.effective_municipality`, which is already
lowercase/canonical), which is exactly why this was never caught. 842 tests
passing, ruff clean (machine A, mocked). **Not yet re-verified against real
Machine B traffic.**
